# 检查维度与判定标准

本文件定义知识库体检的五大检查维度、严重级别判据，以及必须排除的误报类型。

## 维度一：分类与目录结构健康度

好的知识库目录像一条清晰的工作流，让「人和 AI 拿一份东西进来时，最多犹豫两秒就知道该放哪」。

### 重点查什么
1. **分类逻辑打架**：同一层目录下混用了多种维度（例如按部门、按文件类型、按处理状态混在同一级），导致一份文档同时能放两三个地方。
2. **文件放错层（污染 AI 上下文）**：
   - 外部刚收集的文章、课程笔记还没消化验证，直接放进了正式「方法论／业务标准／SOP」目录，AI 会把别人的说法当成你自己的做法；
   - 写到一半的草稿、测试文档和正式成品混在同一个目录里。
3. **空夹泛滥与层级过深**：超过 4 层的深目录会显著增加 AI 检索成本；长期空置且非新近建库的空文件夹容易让人和 AI 迷惑。
4. **命名漂移**：同一类目录一会儿叫 `01-输入`、一会儿叫 `01_输入`，或同一层出现两个语义高度重合的文件夹（如同时有 `外部资料` 和 `内容学习`，或同时有 `历史` 和 `归档`）。

### 级别判定
- 同一层出现语义重复的双生文件夹，或外部未验证资料大量混入正式标准区 → **⚠️ 需要你拍板**（给具体合并或分层方案）。
- 个别空文件夹或层级偏深 → **💡 顺手优化**。

## 维度二：过期与无效文件

AI 扫描文件夹时，往往分不清「这份 2024 年的旧流程已经废了」。过期的文件留在活跃目录，是最常见的 AI 幻觉源头之一。

### 重点查什么
1. **散落在各处的「历史／旧版／备份」子夹**：例如每个部门或主题下都藏着一个 `历史/`、`旧流程/`、`备份/`。只要它们还在活跃目录树里，AI 递归检索就可能顺手读进去。应建议统一迁入根级或分区级 `归档/`（并在协作说明写明「归档不读」）。
2. **明显过时的规则、价格、定位或流程**：文件里写着已废止的旧日期、旧版本号、旧产品名，或与新版本明显冲突。
3. **无用临时残渣**：带 `副本`、`copy`、`测试`、`tmp`、`新建文本文档` 字样、空文件（0 字节）、或长期未动且无实质内容的废草稿。

### 处置建议三选一
- **移入归档（默认推荐）**：曾经有用、以后可能查账或留证据的旧资料 → 进统一 `归档/`，AI 日常不读。
- **合并更新**：旧文件里还有几条有用的补充，但主文件已更新 → 把有用段落并入新文件，旧文件再归档。
- **建议删除**：确认是 0 字节空文件、完全重复的副本、或无价值的临时测试文件 → 列出路径，等用户明确说删才删。

### 级别判定
- 活跃业务目录下散落 `历史/`、`旧版/`、`备份/` 子夹，或存在 0 字节无效垃圾文件 → **🔴 必须处理**。
- 长期未修改（如超 90—180 天）且疑似过期的规范／草稿 → **⚠️ 需要你拍板**（切忌单凭修改时间久就判过期，很多核心原理和经典案例本来就不需要天天改！）。

## 维度三：待沉淀与积压排查

很多知识库不是缺资料，而是「进来的全堆在入口，做完的全停在半路」。

### 重点查什么
1. **入口区积压**：`收件箱/`、`输入/`、`待处理/`、`内容学习/`、`录音/待处理/` 里超过 30 天未处理的原始材料。
2. **审核区滞留**：`待审核/` 里长期没人审批放行的新卡片或草稿。
3. **半成品与完结项目滞留**：`项目库/`、`待发布/`、`草稿/` 里停了很久的文件夹——确认是不是其实已经做完／发完了，只是忘了把能复用的干货（项目案例、一线经验、SOP 改进、金句、复盘结论）提炼沉淀出来再归档。

### 核心判断问题
对每一批积压，帮用户把选择压成三句话之一：
- **值得沉淀**：挑出最有价值的几份，建议先用对应技能（如 `sj-recording`、`sj-learning` 或整理成卡）把干货提炼进知识库，原件再归档；
- **纯囤积未看**：提醒「放了 N 天没打开过」，建议直接移入 `归档/囤存待用` 或清理，别让它天天占视线；
- **仍在进行中**：保留原位，标记正常。

### 级别判定
- 积压和待沉淀问题一律归 **⚠️ 需要你拍板**（AI 不替用户决定哪些囤的资料不要了）。

## 维度四：重复与冲突排查

### 重点查什么
1. **完全相同内容的重复文件**（脚本通过 SHA-256 精确抓出）：通常是多次复制、同步冲突或换工具导出造成的，白占上下文。
2. **不同位置的同名文档**：例如两个目录里各有一份《报价说明.md》或《账号定位.md》，改了一处漏了另一处。
3. **语义冲突的多份规则或 SOP**：同一件事写了两个不同版本（比如一处写「每周复盘」，另一处写「每月复盘」，或者单价、流程步骤打架）。
4. **Skill 堆积与冗余**（如库内管理了 `skills/`）：检查有没有两个 Skill 干同一件事、或者堆了几十个装了从来不用的 Skill——Skill 越多，AI 越容易调错。

### 级别判定
- 内容完全一致的重复文件 → **🔴 必须处理**（建议保留正本，另一份归档或删除）。
- 同名但内容不同的平行文件、规则冲突、冗余 Skill → **⚠️ 需要你拍板**（给出两份差异摘要和倾向建议）。

## 维度五：多 Agent 协作说明一致性与分区安全

现代知识库常常会被多个 AI 工具轮流打开：Claude Code 读 `CLAUDE.md`，Codex / Antigravity 读 `AGENTS.md`，Gemini CLI 读 `GEMINI.md`，Cursor 读 `.cursorrules` / `.cursor/rules/`，WorkBuddy 或人工看 `知识库说明.md`。

### 重点查什么
1. **多端规则文件脱节**：同一目录下同时存在 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md` 等，但内容哈希不一样（也不是软链接指向同一份）——意味着你在一端新加的禁区或改过的目录，换个工具 AI 完全不知道。
   - **最佳实践建议**：若环境支持软链接，维护一份真身，其余指向它；不支持软链接（如部分 Windows 同步场景），每次改完同步覆盖其他端，并在末尾注明同步日期。
2. **目录地图与路径死链**：协作说明里写着「把稿件存进 `04-内容生产/待发布/`」或引用了某份模板路径，但磁盘上这个目录已经改名或删掉了。
3. **幽灵 Skill 引用与漏记**：规则文件里让 AI 调用某个不存在的 Skill，或者磁盘里新装了核心 Skill 却没写进说明。
4. **常驻规则文件过长**：主规则文件超过约 4000—5000 字，往往是把长篇背景资料、全量案例或过时日志塞进了每次对话必读的入口，浪费上下文还稀释核心铁律。
5. **共享区敏感信息抽检**（仅当库内区分了「共享区／团队区」与「私有区」时）：抽查共享区里是否误放了报价底线、成本利润、合同原件、未脱敏手机号／微信号或密钥文件。

### 级别判定
- 同目录多端主规则文件不同步、规则文件里的活路径死链、共享区疑似混入敏感文件 → **🔴 必须处理**。
- 常驻规则文件偏长需要瘦身、规则中漏列新 Skill 或新分类目录 → **⚠️ 需要你拍板**。

## 常见「看着像问题、其实不是问题」的误报避坑表

执行语义判断时，先对照下表把误报过滤掉：

| 现象 | 为什么不是问题 | 处理方式 |
|---|---|---|
| 核心方法论、原则卡、经典案例超过 90 天没修改 | 稳定不变的知识本来就不需要天天改 | **忽略**，绝不按修改时间判过期 |
| 刚建库不久，某些预留目录（如 `方法论/`、`归档/`）是空的 | 正常的流程预留位 | 结合库龄判断，必要时仅放 💡 |
| 规则文件里带 `[产品名]`、`<账号名>`、`{日期}` 的路径磁盘上不存在 | 这是模板占位符，不是具体路径 | 脚本已自动忽略，不报死链 |
| 历史更新日志里写着「已删 `旧路径`」「原目录已迁走」 | 记录历史变更，本来就该不存在 | 脚本按行排除，不报死链 |
| 统一 `归档/`、`备份/` 目录内部存在旧链接或老文件 | 归档区本来就是历史快照，且 AI 不读 | 不对归档区内部报死链或陈旧 |
| 工具自带隐藏目录（`.obsidian/`、`.git/`、`.stversions/`、`.DS_Store`） | 软件运行所需元数据 | 脚本默认跳过，不纳入业务体检 |
| 多个子目录下都叫 `账号卡.md`、`SKILL.md`、`_说明.md`、`README.md` | 标准化的固定结构文件名 | 脚本白名单已放行，不报同名重复 |
| 多端规则文件通过软链接指向同一份真身 | 本身就是同一份文件，天然同步 | 判定为「✅ 已同步」 |
