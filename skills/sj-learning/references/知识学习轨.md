# 知识学习轨

## 从问题到证据

不要按「每段摘要」机械缩写。先找作者要解决的核心问题，再把主张、推理、方法与案例接到这个问题上。文中存在支线或互不相关的部分时，分开记录，不强造一个统一理论。

| 提取项 | 要回答的问题 | 常见失真 |
|---|---|---|
| 核心问题 | 作者到底在回答谁的什么困难？ | 把标题口号当成正文论题 |
| 核心主张 | 作者建议相信或采取什么？在什么条件下？ | 删除限定词，改成普遍规律 |
| 概念与术语 | 作者如何定义？和常见含义有何区别？ | 只抄名词，不保留区分作用 |
| 框架与方法 | 输入、步骤、输出、判断点是什么？ | 把分类框架误写成行动顺序 |
| 案例与证据 | 谁做了什么、结果如何，能证明哪一小段主张？ | 一次成功外推到所有人 |
| 反例与边界 | 什么时候无效，作者遗漏了什么？ | 只提正例，替作者补上未讲过的答案 |

标题问题和正文问题不一致时都写出来。例如标题承诺「如何持续写作」，正文实际只讨论「如何找第一篇素材」，学习结果应保留这个范围差异。

## 保留判断的主人

用四种标签表达证据状态：

- **原文陈述**：原文可见的陈述或数据，注明谁说的；尚未独立验证。
- **作者解释**：作者对原因、意义、机制的解释或价值判断。
- **学习者归纳**：将多段内容组织成框架，说明不是作者原有命名。
- **待验证假设**：对其他场景的推测、因果解释或应用建议。

「作者报告使用某方法后增加咨询」是可定位的原文陈述；「该方法导致咨询增长」需要更多证据。不要把同一时间发生写成因果，也不要因为材料详尽就标为已核实事实。

需要外部事实核查时，只在当前任务范围内使用可用的可靠来源；无法核查就标待核。学习作者观点不等于逐条上网查证，但不能把未核实数字当权威依据推荐。

## 方法要能执行

对真正的方法还原以下字段；原文没讲的写「未说明」，可以另给补充建议，但不混入原方法。

```markdown
方法名：
解决的问题：
适用对象与前提：
所需输入：
步骤与每步产物：
关键判断点：何时进入下一步，何时停止或换办法
输出与验收：
失败情形与不适用场景：
来源位置：
原文未说明的部分：
```

框架可能只是分类工具，例如把客户问题分成价格、时间、信任；不能擅自写成「先解决价格，再解决时间，最后建立信任」的三步流程。

## 案例与证据

记录背景、当事人、动作、结果、时间顺序、可比较的基线与来源。缺基线时不要自行算增长率；用户没有实践该案例时，不能成为其个人素材。

每个案例附一句「支持什么／不能证明什么」。作者的一个亲历案例可帮助理解方法如何使用，但不能证明它适用于所有行业。若原文给了失败案例，保留失败原因和限制，不能只留下成功故事。

## 关系与冲突

只对照当前任务明确提供或授权读取的既有知识。

| 关系 | 怎么处理 |
|---|---|
| 重复 | 引回已有结论，保留更清晰的解释或来源，不再制造平行卡 |
| 补证据 | 新增案例、反例或条件，区分是否独立来源 |
| 修正 | 说明旧结论少了什么条件；新材料不足时不要宣布推翻 |
| 冲突 | 两说并列，列各自对象、条件与证据，留下可检验问题 |
| 全新 | 解释它补了哪个具体问题；没有用途也可只留在本篇笔记 |

同一篇被多次转载，不算多个独立证据。两个来源观点一致，也不自动变成普遍事实。

## 应用到自己的条件

用户明确要把知识或写法用到当前任务，且已给相关材料时，再做这一步。先并列原方法的适用对象、所需输入和关键前提，以及用户材料能确认的对应条件；只比较会影响本次选择的项，不另开一轮背景问卷。原文没说的前提标「原文未说明」，由学习者推测的前提单独说明。

每个准备使用的方法选择一种处理，不为填表强行用齐四类：

| 处理 | 适用情况 | 要交代什么 |
|---|---|---|
| 沿用 | 关键前提符合，现有材料能执行 | 沿用哪一步，以及仍需观察的结果 |
| 改写 | 要解决的问题相近，但输入、资源或使用场景不同 | 改哪一步、为什么改；改写部分是本次应用建议 |
| 不采用 | 方法要解决的问题不同，或已知前提不成立 | 哪项差异让它不适合；不因为作者做成过就硬套 |
| 待验证 | 关键条件未知，现有证据还不能选择 | 缺什么，以及哪项小检查能改变判断 |

随后完成一个与当前任务直接相连、规模足够小的产物：例如用已有素材写一段开头、把一项决定做成比较表、给一条需求写答疑提纲。验收要能指出具体位置，如「开头是否回应给定问题」「表格是否保留两种选择的代价」。不采用某方法时，可交一张注明不适用原因和缺口的选择记录，不另编一个作业；待验证时也不必先做完整成品。

**教学示例（虚构）**：原文方法是「汇总一周同类咨询，按重复问题选择答疑题」。用户只有一条留言「租房不想在墙上打孔，厨具怎么挂」，另提供了一份免打孔挂架的安装步骤，希望先写一条答疑。

- 原方法前提：有一段时间的同类问题，可比较重复情况。自己的条件：只有一条留言和一份步骤，不能判断高频，但能回应一个明确问题。
- 处理：改写。保留从实际问题取题的做法，暂不做频次排名；这不是高频需求已经成立。
- 小产物：答疑提纲——「适用于安装步骤注明的墙面与挂架→按原步骤安装→按材料注明的要求检查→材料未提供的承重或拆卸信息列待补」。正文不擅填墙面类型、承重数字和免损承诺。
- 检查：每一步是否能回到那份安装材料，是否直接回应「不打孔」的需求，缺失条件是否可见。实际安装与读者反馈未发生，不能记为方法已验证有效。

没有应用请求时，做到知识还原或写法拆解即可。用户只说想用但没给自身材料时，可以先说明所需条件与待验证项，不自动检索其历史，也不把教学示例换成用户亲历。

## 知识轨交付样式

先给核心问题和简短知识地图，再按重要性写少量可追溯的条目。每条至少包含：结论归属、来源位置、证据、适用条件和可尝试的动作。条目多少由材料决定，不为凑数拆碎，也不因固定上限漏掉影响结论的反例。
