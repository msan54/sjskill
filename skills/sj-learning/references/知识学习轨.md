# 知识学习轨：这篇讲了什么

不按段落一段段缩写。先找到作者要回答的那个问题，再把主张、方法和案例挂到这个问题上。文章里有跟主线无关的支线，分开记，不硬拼成一套理论。

## 一、按顺序提这七样

1. **核心问题**：作者真正想回答什么。标题问的和正文答的不一样，两个都记下来——比如标题许诺「怎么坚持写作」，正文只讲了「第一篇的素材从哪来」。
2. **核心主张**：作者的结论是什么、在说谁、在什么范围内成立。限定词别删：把「新手的前三个月」删掉，就成了谁都适用的规律。
3. **概念与术语**：作者怎么定义的，和平常的用法有什么不同。
4. **框架与方法**：要什么输入、分几步、产出什么、怎么判断好坏、边界和例外。原文没说的写「未说明」，不替作者补。分类框架不是步骤：作者把客户的顾虑分成价格、时间、信任三类，不能写成「先解决价格，再解决时间，最后建立信任」。
5. **案例与证据**：什么事、谁、做了什么、结果怎样、数据多少，以及它能证明什么、证明不了什么。一个人做成了，证明不了所有人都能做成。
6. **反例与争议**：什么情况会失败、作者没回答的问题、证据薄的地方、还有没有别的解释。
7. **和用户已有知识的关系**：用户有知识库，就和 `方法论/`、`素材库/` 里同主题的比——重复、补证据、升级修正、冲突，还是全新。没有知识库就写「没有可对照的已有知识」。

## 二、每个判断分清是谁的

- **事实**：原文写出来的事和数据，注明谁说的。写出来不等于已经核实。
- **作者观点**：作者对原因、意义的解释和判断。
- **AI 归纳**：把几段内容整理成的框架；名字是 AI 起的，就写明不是作者的说法。
- **待验证假设**：搬到别的场景能不能用、因果对不对，还要试。

「作者说用了这个方法之后，来咨询的人多了」是事实（作者说的）；「这个方法让咨询变多」是待验证的因果。前后发生的两件事，不写成因果。

## 三、方法要写到能照做

真正的方法按这几项还原，原文没讲的写「未说明」，你想补的建议另起一行写，不混进作者的方法：

```markdown
方法名：
解决什么问题：
适合谁，前提是什么：
要准备什么：
分几步，每步出什么：
怎么判断该进下一步，什么时候停下来换办法：
做完怎么验收：
什么情况下不适用：
在原文哪里：
原文没说的部分：
```

## 四、和已有知识比

| 关系 | 怎么处理 |
|---|---|
| 重复 | 指回已有的那条，不另起一条 |
| 补证据 | 补上新的案例、反例或条件，写清是不是独立的来源 |
| 升级修正 | 写清旧结论少了什么条件；证据不够，不说「推翻了」 |
| 冲突 | 两说并列，各写对象、条件和证据，留一个能检验的问题 |
| 全新 | 写清它补上了哪个具体问题 |

同一篇被转载多次，不算多个独立证据；两个人说法一样，也不等于成了普遍事实。

## 五、最该立马执行的事（用户问「学完该干嘛」时才写）

- 最多 3 件，每件写清：做什么、为什么是现在、大概花多久。
- 选不出 3 件就写 1 件；一件都选不出，直说「这篇对你现在的业务没有能直接做的事」，不硬凑。
- 按用户眼下最要紧的事挑，不按文章篇幅挑。用户没说过他在忙什么，先问一句，不替他编处境。
- 知识多不等于该做的事多。

## 六、知识轨怎么交

先给核心问题和一张简短的知识地图（问题 → 主张 → 依据 → 方法 → 边界），再按重要性写几条能追溯的知识，每条带：谁的结论、在原文哪里、证据、什么情况下成立、可以试的动作。条数由文章决定，不为凑数拆碎，也不漏掉会改变结论的反例。
